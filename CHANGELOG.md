## [Unreleased]

### Added
- **Animaciones** (opt-in: `features.animations`). Nueva sección "Animaciones" en el tab Tema, con `theme.animations`: `cardEntrance`, `categoryEntrance` y `headerEffect` (`none` / `fade` / `scale` / `slide-up` / `slide-down` / `slide-left` / `slide-right` / `blur`), compartiendo `cardEntranceDuration` (100-2000 ms), `cardEntranceStagger` (0-300 ms, escalonado que se corta en el elemento 12 para que el último no aparezca después de que el usuario ya scrolleó), `entranceEasing` (`ease-out` / `ease-in-out` / `linear` / `spring`) y `entranceDistance` (4-64 px, sólo para los slides); `entranceTrigger` (`load` o `scroll`, este último con un `IntersectionObserver` inline que sin JavaScript no esconde nada); `cardHover` (`default` / `none` / `lift` / `grow` / `glow` / `tilt`) con `hoverDuration` (0-600 ms, default 180 = el valor histórico); más `titleTypewriter`, `counters` y `respectReducedMotion`. **Todos los defaults son "sin animación"**: prender la feature no cambia nada de lo que se ve hasta que elijas un efecto. La entrada de tarjetas y el header se generan como CSS en el servidor (`src/lib/animations.ts`, mismo patrón que `computeCardSpanCss`) en vez de envolver las tarjetas en componentes, porque un elemento intermedio se convertiría en el hijo del grid y rompería el ancho de `data-span`. El título con máquina de escribir y el contador de apps de la status bar usan `@astroanimate/core` (MIT, bundleado vía `ssr.noExternal`, sin CDN ni fetch externo) y sirven el texto completo en el HTML, así que sin JavaScript se ven normales. Labels y ayuda en `es`/`en`/`pt`.
- **Las animaciones se ven en la vista previa del tema.** La miniatura del admin usa el mismo `computeAnimationCss` que la portada, apuntando a su propio markup vía `AnimationTargets`, en vez de una segunda implementación que se desincronizaría. Cada edición renombra los `@keyframes` con un sufijo, que es lo que hace que el navegador vuelva a reproducir la animación: sin eso el CSS cambia pero no se ve nada. El disparo por scroll se muestra como "al cargar", porque en la miniatura no hay scroll que lo dispare. Botón "Repetir en la vista previa" para volver a verla cuando quieras.
- **Guard global de `prefers-reduced-motion`**. Quien pidió menos movimiento en su sistema operativo ya no ve animaciones ni transiciones en ningún lado, sin importar la config del tema. Antes no había **ni un** `prefers-reduced-motion` en el CSS. Las animaciones opt-in traen además su propio guard (desactivable con `theme.animations.respectReducedMotion`, aunque el guard global sobre transiciones se mantiene igual).
- **Sistema de feature flags opt-in** (`features.*` en `config.json`). Infraestructura base para que las features nuevas (markdown, tags, pinned, presets, i18n, webhooks, QR, multi-user, OIDC, multi-portal, etc.) sean **opt-in**: default `enabled: false` para todas, el admin las prende desde `/admin → Avanzado → Features`. Cada switch muestra label, descripción corta, ola del roadmap, marca experimental si aplica, y qué deps npm carga. Principio 7 del roadmap: "si no la usás, no la pagás". Cero costo de runtime / deps / UI para features apagadas. Helper `isFeatureEnabled(config, name)` en `src/lib/features.ts` para gating en server-side, `loadFeatureModule(config, name, importer)` para imports dinámicos condicionales.
- **i18n de la UI** (opt-in: `features.i18n`). Tres locales soportados: `es` (default histórico), `en`, `pt`. Módulo `src/i18n/` con diccionarios planos (dot-notation) + función `t(locale)` con interpolación ICU-lite (`{varName}` y `{n, plural, one {#} other {#}}`) sin dependencias externas. Strings traducidas: portada pública (header, search, mode toggle, OG meta, locked categories), admin (nav, tabs del dashboard, toasts, login), componentes (`Search`, `Clock`, `RefreshButton`, `ThemeScript`). Resuelve locale por prioridad: cookie visitante (`umbral_locale`, 30 días) → default admin (`features.i18n.locale`) → `Accept-Language` → `es`. Override por visitante via `<LanguageSwitcher>` (dropdown nativo en el header). Endpoint público `POST /api/locale` (form-urlencoded o JSON) para setear la cookie. Si la feature está apagada, todo el UI permanece en español sin overhead (principio 7).
- **Visor de audit log** (opt-in: `features.auditLogViewer`). Nueva sección "Auditoría" en el tab Avanzado del admin. Lee `data/audit.log` (que ya rotá a 10MB con 3 backups) y muestra las últimas N entries en una tabla con sticky header y scroll virtual. Filtros: dropdown de acción (auto-poblado con las acciones distintas del log), substring case-insensitive sobre el `detail`, rango `desde/hasta` (datetime-local en UTC). Botón "Limpiar" resetea filtros; "Descargar log completo" baja las últimas 1000 entradas como archivo `.log`. Parser en `src/lib/audit.ts` (TSV: `timestamp\tacción\tdetalle`), formato reverse-chronological. Endpoint `GET /api/audit` con query params (limit cap 1000, validaciones de ISO timestamp, 404 si la feature está apagada). `?actions=1` devuelve la lista de acciones para popular el dropdown. Sin dependencias nuevas — usa el cache de `getConfig()` + `fs.readFile`.
- **Markdown en descripciones de tarjetas** (opt-in: `features.markdown`). Las cards pueden tener descripciones en Markdown (GitHub-flavored) además de plain. Límite ampliado: 200 chars para plain, 1000 para markdown. Render server-side con `marked` + `DOMPurify` (mismas libs que ya usa la app — cero deps nuevas). Whitelist explícita de tags permitidos (`a, b, i, em, strong, p, br, ul, ol, li, h1-6, blockquote, code, pre, table, img`) y atributos (`href, title, alt, src, class`); `href` con protocolo no-http (`javascript:`, `data:`, etc.) se bloquea. Defense-in-depth: si la feature está apagada, el server fuerza `descriptionFormat: 'plain'` y clampea a 200 chars aunque alguien mande `descriptionFormat: 'markdown'` por la API. UI del admin: toggle "Markdown" + preview en vivo (render client-side con las mismas libs vía dynamic import) + contador de chars. `Card.astro` decide el formato de render según `descriptionFormat` del card + estado de la feature (no confía en el JSON).
- **Tags en tarjetas** (opt-in: `features.tags`). Array opcional `tags: string[]` por card, max 10 tags kebab-case lowercase (regex `^[a-z0-9-]{1,30}$`, 30 chars max por tag). Las tags son **cross-cutting** (complementan la categoría con dimensiones alternativas como "urgent", "frontend", "legacy"). Sanitización en el schema via `z.preprocess`: lowercase + trim + guiones + dedup + cap 10. Defense-in-depth: si la feature está apagada, el server dropea `tags[]` aunque venga en el JSON (validado con bypass attempt). Búsqueda en la portada incluye tags via `data-tags` attribute (ThemeScript agrega las tags al texto searchable). UI del admin: chip input con Enter/coma/espacio para agregar, Backspace borra el último, autocomplete muestra hasta 8 tags existentes en otras cards, dedup client-side, contador "X/10". Las tags se muestran como chips pequeños al lado del URL en la lista de cards.
- **Tarjetas fijadas (pinned)** (opt-in: `features.pinned`). Boolean opcional `pinned: boolean` (default `false`) por card. Las cards pinned se renderizan **primero** en su categoría, independientes del `order` numérico. Sort: pinned DESC, después order ASC. Indicator visual: emoji 📌 al lado del título en la portada + en la lista del admin. Defense-in-depth: si la feature está apagada, el server fuerza `pinned: false` aunque alguien mande `pinned: true` por la API (validado con bypass attempt). UI: checkbox "Fijada" en el card editor (sólo si la feature está activa) + badge en la card list. Cero deps nuevas.
- **Webhooks de notificación** (opt-in: `features.webhooks`). Convierte a Umbral en un **centro de notificaciones activas**: cuando una card con `healthCheck: true` cambia de estado (healthy → failing, o viceversa), Umbral hace POST a las URLs configuradas. Schema: `webhooks.items[]` con id, name, url (http(s) only), events (`health_fail`, `health_recover`), `minFailures` (cuántas fallas consecutivas antes de disparar; default 3), `cooldownMin` (minutos entre notificaciones del mismo webhook; default 30), `enabled`. Engine en `src/lib/webhooks.ts`: state machine en memoria (contadores de fallas consecutivas + último fire por webhook), dispara en cambio de estado con cooldown. Payload: JSON crudo con headers `X-Umbral-Event`, `X-Umbral-Card`, `User-Agent: Umbral-Webhook/1.0`. Adaptadores built-in para Slack, Discord, ntfy, Mattermost, Gotify (vía función `adaptPayload()`); custom manda el JSON crudo. Endpoint `POST /api/webhooks/test` para validar un endpoint antes de guardar. Security: SSRF guard (bloquea loopback, private IPs, cloud metadata; respeta `security.network.allowInternalHosts` para deploys LAN); timeout 8s por POST; `redirect: 'manual'` para cerrar bypass por redirect. Wired en `/api/status`: después de cada check, si hay cambio de estado, dispara los webhooks matching. UI admin: lista de webhooks con nombre/URL/eventos/threshold/cooldown, botón "Probar" por webhook, form de alta con campos name/url/events/threshold/cooldown, badge "activo/inactivo". Audit log automático (`webhook_fired` / `webhook_failed`) con cardId y resultado. Defense-in-depth: si la feature está apagada, el engine no se ejecuta aunque haya webhooks configurados. Cero deps nuevas.
- **Ventanas de mantenimiento** (opt-in: `features.maintenanceWindows`). Programa periodos donde una (o todas) las cards están en mantenimiento. Schema: `maintenanceWindows.items[]` con id, cardIds (array, `['*']` para "todas"), startsAt / endsAt (ISO 8601 UTC), reason (max 120 chars), enabled. Validación: `endsAt > startsAt`. Helpers en `src/lib/maintenance.ts`: `getActiveWindowsForCard(cardId)` (devuelve windows activas que aplican a esa card), `isWindowActive(w)`, `getMaintenanceSummary()` (activas + próximas + expiradas para dashboard), `formatRemaining(ms)`. Render: badge ámbar 🔧 con la razón en la portada (vía prop `maintenanceReason` en `Card.astro`). Integración con webhooks: si una card está en maintenance window, el engine **suprime** `health_fail` (el admin sabe que está fallando) pero **sigue disparando** `health_recover` (señal de "OK, volvimos"). UI admin: lista de windows con active/expired indicator + remaining time, form de alta con cards selector (multi o all), datetime-local UTC inputs, reason. Defense-in-depth: si la feature está apagada, el array se dropea en saveConfig y el render ignora las windows. Cero deps nuevas.
- **Métricas de latencia** (opt-in: `features.metrics`). Ring buffer en memoria por card (últimas 100 samples = ~1.5h con check cada 60s). Schema: agregado `latencyThresholdMs` por card (warning si la latencia supera threshold; default 0 = sin warning). Módulo `src/lib/metrics.ts` con `recordSample()`, `getSamples()`, `getCardSummary()` (avg, p95, max, lastOk), `sparklineSvg()` (path SVG inline, sin libs). Wire-up en `/api/status`: cada check registra una muestra (con ok y latencyMs) — el try/catch/finally captura successes y failures. Render en la portada: sparkline SVG inline al lado del dot de health check, fetch client-side cada 60s. UI admin: nueva sección "Métricas" con tabla (card / avg / p95 / max / último / sparkline), filtro de rango (10min / 1h / 24h) y límite de samples. Endpoint `GET /api/metrics` con query params `id`, `range`, `limit`, `summary`, `svg` (devuelve path SVG inline en vez de JSON). Cero deps nuevas.
- **QR codes** (opt-in: `features.qr`). Endpoint público `GET /api/qr/:cardId.png` (con `?size=200&margin=2&format=png|svg`) que devuelve el QR de la URL de la card. Lib `qrcode` (~30KB, dep nueva). Resuelve URLs relativas (/docs) usando `BASE_URL` env o el origin del request, así el QR escaneado desde el celular abre la URL correcta. UI: botón QR (icon top-right) en `Card.astro` (sólo para cards de tipo `link` y cuando la feature está activa) que abre el PNG en una nueva tab. Defense-in-depth: si la feature está apagada, el endpoint devuelve 404, el botón no se renderiza, y el URL público no procesa QRs. Cero overhead cuando está apagada.
- **Multi-user con roles** (opt-in: `features.multiUser`). El password único (super-admin) sigue funcionando como "rescue path" por default; el admin puede crear usuarios con username y rol (`admin` / `editor` / `viewer`). Schema: `auth.users[]` con id, username (kebab-case), displayName, passwordHash (bcrypt cost 12), role, userEpoch (per-user — para invalidar sesiones de un user sin tocar a los demás), createdAt, lastLoginAt. `auth.singlePasswordEnabled` toggle (default true) para "Solo password unico" / "Password + usuarios" / "Solo usuarios" (con confirmación dura si quedás sin users). Login: soporta `{password}` (legacy) o `{username, password}` (multi-user). Token session: `<id>.<authEpoch>.<userEpoch>.<hmac>` — authEpoch global para invalidar todo, userEpoch per-user para cambios granulares. UI: nueva sección "Usuarios" en el tab Password con lista (chip de role con color), botones de cycle role, reset password (incrementa userEpoch), remove, form de alta con kebab-case username. Defense-in-depth: si la feature está apagada, `users[]` se dropea al guardar (validado con bypass attempt).
- **2FA / TOTP** (opt-in: `features.totp2fa`). Cada user puede activar un segundo factor de autenticación compatible con Google Authenticator / Authy / 1Password / Bitwarden / etc. (RFC 6238 / TOTP-SHA1, 6 dígitos, 30s). Lib `otpauth` (~10KB, dep nueva). Módulo `src/lib/totp.ts` con `generateTotpSecret()`, `getQrCodeUrl(username, secret)` (genera URL `otpauth://` para el QR), `verifyTotp()`, y cifrado AES-256-GCM del secret con key derivada de `SESSION_SECRET` vía HKDF-SHA256 (defense-in-depth: si el admin rota `SESSION_SECRET`, los secrets TOTP existentes se invalidan y el admin debe re-configurar 2FA por user). Login flow en 2 steps: 1) password + username → si el user tiene `totpSecret`, server devuelve `{requiresTotp: true, partialToken}` (TTL 5min, single-use); 2) POST `{partialToken, totpCode}` → verifica y emite sesión final. **Importante**: el password único super-admin NO puede protegerse con TOTP (intencional — es el rescue path final). Si perdés acceso a los TOTP seeds, el password único te deja entrar y desactivar 2FA de los users. Solo los users de `users[]` pueden tener TOTP. Cero overhead cuando la feature está apagada.
- **Multi-portal (Ola 4.1) — base sólida, data per-portal en v2**. Esta ola entrega la infraestructura conceptual: schema `portals[]` con id/name/host/pathPrefix, helpers `resolvePortalId(request, cfg)` (match por Host header o path prefix, con soporte de wildcards `*.example.com` y `*`), `migrateLegacyToMultiPortal()` (mueve automáticamente `data/` → `data/portals/default/` cuando la feature se prende, idempotente), y paths helpers (`portalConfigPath`, `portalUploadsPath`, `portalAuditPath`). Defense-in-depth: si la feature está apagada, `portals[]` se dropea al guardar. El data layer per-portal (que `getConfig` lea de `data/portals/<id>/config.json` en vez de `data/config.json`) queda como follow-up en v2 de esta feature — el refactor es significativo (toca el cache, el loadFresh, todos los endpoints que leen config) y requiere una session de focus dedicada. En esta v1, multi-portal es **config-only**: cada portal es una instalación separada detrás de un reverse proxy, o se opera con la versión v2 cuando esté lista. La schema, los helpers, la auto-migration y el UI (a continuación) son válidos y testables. UI pendiente: lista de portales en Avanzado + form de alta/edición.
- **OIDC / SSO (Ola 3.3)** — login con OpenID Connect (Keycloak, Google Workspace, Authentik, Azure AD, etc.). Schema `oidc.providers[]` con id/name/issuer/clientId/clientSecret/scopes/claimMap (mapea claims a campos de user: username/email/displayName/role)/autoProvision (crear user automáticamente si no existe)/defaultRole. **Default OFF** — incluso para instalaciones nuevas, el admin debe explícitamente configurar un provider. Esto es por diseño: OIDC cambia el flow de auth (nuevas rutas, nueva superficie de ataque), queremos que se active explícitamente. `src/lib/oidc.ts` implementa el flow Authorization Code + PKCE S256 (RFC 7636) sin librerías externas (200 LOC, stdlib only): discovery via `/.well-known/openid-configuration` (cacheado 1h), state + nonce + code_verifier con storage en `Map` in-memory (TTL 5min), token exchange, id_token claims extraction. Endpoints: `GET /api/auth/oidc/:providerId/start` (redirige al IdP con state cookie firmado) y `GET /api/auth/oidc/:providerId/callback` (canjea code, valida nonce/iss/exp/aud, auto-provisiona user si corresponde, emite session token). **Password único super-admin sigue siendo el único path que NO requiere OIDC** — intencional, es el rescue path. Cero deps nuevas.
- **Multi-portal data layer COMPLETO (Ola 4.1)** — refactor del data layer en `src/lib/config.ts` para que cada portal tenga su propio `data/portals/<id>/config.json` + `uploads/` + `audit.log`. APIs `setActivePortalId(id)` / `getActivePortalId()` para que el middleware setee el portal por request. Auto-migration sigue funcionando (data/ → data/portals/default/ cuando se prende la feature). Backwards compat 100%: con la feature apagada, todo el comportamiento es idéntico a v1.x (lee/escribe en data/config.json). Con la feature prendida, se hace dispatch del portal activo al hacer I/O. Funciona con la estrategia "1 instancia = 1 portal" (la más común); para multi-portal real en una sola instancia con cache in-memory per-portal, queda como v2 (cache es la parte compleja).
- **API tokens (Ola 4.2 server-side)** — schema `apiTokens.items[]` con id/name/scope (read|write)/expiresAt/lastUsedAt/tokenLast4/revoked. Tokens se crean vía admin (UI pendiente) y se identifican vía `Authorization: Bearer umb_xxx`. El plaintext se devuelve UNA sola vez al crear — sólo guardamos bcrypt hash. `src/lib/api-tokens.ts` con `verifyApiToken(request)` (O(n) sobre tokens, típicamente <10) y `generateApiTokenPlaintext()`. Endpoint `GET /api/config` ahora acepta tokens API: si el request trae `Authorization: Bearer umb_xxx` válido (con `features.apiTokens` ON), responde igual que con sesión admin. Esto permite que integraciones externas (CI/CD, scripts, el CLI) consuman la API sin cookies de sesión. Audit log automático (`api_token_used` con id/name/scope). Defense-in-depth: si la feature está apagada, los tokens no se persisten (dropeados al guardar).
- **CLI (Ola 4.2) — scaffold Node + `tsx` en `packages/cli/`** — primer release del CLI para gestionar Umbral vía API. Comandos: `config get/backup`, `cards list/add`, `users list`, `tokens list`, `health`. Auth via `UMBRAL_TOKEN` env var o `--token` flag. Cero deps externas (solo `tsx` para ejecutar TS directo). Estrategia: **este CLI Node es la spec funcional** que se va a portar a Rust en un repo separado (recomendado para producción — binario único, sin `node_modules`). El puerto Rust queda como follow-up; mientras tanto, este CLI funciona via `npx tsx` o instalando en `packages/cli/`. Tests manuales OK (ver `packages/cli/README.md` para el path de port-to-Rust).
- **Drag-and-drop para categorías** en el panel admin (pestaña Categorías). Cada fila tiene un handle `⋮⋮` a la izquierda; arrastrar reordena el array `cfg.categories` y el cambio se persiste con "Guardar cambios". El home ahora respeta ese orden: las secciones/columnas aparecen en la portada en el mismo orden que las ves acá. Bug fix de paso: antes el orden de los grupos en la portada dependía de cuál era la primera card de cada categoría (no del array de categorías) — ahora se ordena por la posición de `catId` en `config.categories`. Categorías huérfanas (cards con un category que ya no existe) caen al final.

### Changed
- **Admin desacoplado.** `dashboard.astro` pasó de 4889 líneas a componentes por dominio: los 17 tabs que quedaban inline y los 5 modales se movieron a `src/components/admin/` (el editor de tarjetas se subdividió en `CardEditorFields` + `IconPickerPanel`), sobre una base nueva de componentes genéricos en `src/components/admin/ui/` (`HelpIcon`, `FormGroup`, `RangeField`, `ToggleField`, `SelectField`, `ColorField`, `Modal`, `EmptyState`, `TabBar`, `Badge`) que absorbe la duplicación de ~400 bloques de formulario. El HTML renderizado no cambia: se verifica con `astro/container` en `tests/admin-ui.astro.test.ts`, `tests/admin-panels.astro.test.ts` y `tests/admin-modals.astro.test.ts`. El objeto Alpine no se tocó — los componentes son presentacionales y siguen resolviendo contra él. Higiene de paso: el bloque "Cards tab" que vivía en `admin-layout.css` se movió a `admin-cards.css`, donde corresponde.

### Changed
- **El dashboard del admin bajó de ~420 KB de JSON inline a 185 KB de HTML total.** Cada carga serializaba los 8.586 nombres de íconos (229 KB), el catálogo de ayuda ya renderizado (88 KB), las 225 plantillas de apps (55 KB), los presets de tema (11 KB, duplicados con `ThemePresets.astro`) y la metadata de IA (12 KB) — todo para que la mayoría de las sesiones no usara casi nada de eso. Ahora se pide a demanda: la ayuda al abrir un `?`, las plantillas al abrir el modal, el catálogo de packs al entrar al tab, la metadata de IA al entrar al tab, y los nombres de íconos con un fetch que no bloquea el render. Los catálogos estáticos se sirven como rutas prerenderizadas (`/api/help/<locale>.json`, `/api/presets.json`, `/api/ai-meta.json`, `/api/icon-pack-catalog.json`), así que también existen en el build del demo y el navegador las cachea.
- **Se fueron los 190-490 ms de CPU sincrónica por request del dashboard.** Renderizaba las 162 entradas de markdown del catálogo de ayuda en cada GET, bloqueando el event loop para producir siempre el mismo HTML. Ahora se renderiza una vez por locale y por proceso.

### Security
- **El hash del super-admin y el CSRF de la config dejaron de viajar al dashboard.** Sólo se serializan `auth.users` y `auth.singlePasswordEnabled`, que son los campos que el panel de usuarios edita. `saveConfig` además ignora cualquier otro campo de `auth` que llegue en un PUT, en vez de mergearlo.
- **El config completo dejó de viajar al navegador.** Los dos layouts serializaban `data/config.json` entero a `window.__INITIAL_DEMO_CONFIG__` en cada página, incluida la de login sin autenticar y la portada pública, así que cualquiera que abriera `/admin` recibía en el HTML el hash de la password del super-admin, el token CSRF, la API key de IA, las keys de búsqueda externa, los client secrets de OIDC y los seeds TOTP de los usuarios. Ahora el payload existe sólo en el build demo estático (donde `public/demo-runtime.js` lo necesita como semilla) y pasa por `sanitizeConfigForClient()` en `src/lib/client-config.ts`, que borra esos campos. `tests/client-config.test.ts` falla si un secreto vuelve a aparecer o si un layout serializa el config a mano.

### Fixed
- **`theme.footerOpacity` no hacía nada en la portada.** Su única regla CSS vivía en `admin-theme.css`, una hoja que el layout público no importa, y el markup ni siquiera emitía el atributo que la regla buscaba (`.status-bar[data-footer-opacity]`, cuando el elemento es `.status-bar-wrap`). La regla se movió a `global.css` y ahora sigue el mismo patrón que `headerOpacity`.
- **Todos los botones del admin estaban más chicos de lo definido.** `admin.css` redefinía `.btn-sm` más abajo, con un padding pensado para la lista de webhooks, y ganaba por orden de cascada.
- **Cache stale después de `saveConfig`**: `invalidate()` limpiaba `cache` pero no `seedPromise`, entonces `getConfig()` post-save devolvía el config de boot con `features: {}` aunque el disco ya tuviera los toggles guardados. Esto rompía toggles múltiples de features: prender `tags` y después `markdown` reseteaba `tags` a `false` en el save. Fix: `invalidate()` también resetea `seedPromise = null`. Mismo fix beneficia cualquier flujo que dependa de `getConfig()` inmediatamente después de un save (no solo features).
- **PUT /api/config 400 por descripciones largas**: cards con `description` >200 chars (pegados de Wikipedia, devueltos por la IA, etc.) rompían el save. `CardSchema.description` ahora clampea silenciosamente con `.transform((v) => v.slice(0, 200))` en vez de rechazar con `String must contain at most 200 character(s)`. Defense-in-depth en el cliente (`saveAll()` trunca antes de enviar y avisa con un toast si truncó algo).
- **Edit card no carga la categoría**: bug de timing de Alpine 3 — el `<select x-model="editingCard.category">` se inicializaba antes de que el `<template x-for="c in cfg.categories">` hubiera renderizado los `<option>`, así que el select caía al fallback "— seleccionar —" aunque el value en memoria fuera válido. Fix canónico: `x-init="$nextTick(() => $el.value = editingCard.category || '')"`.
- **Console flooded con 502 al auto-completar**: cuando el scraper encontraba una `og:image` o favicon que el origen respondía con 4xx (404, 403, etc.), `/api/upload-from-url` devolvía 502 Bad Gateway y ensuciaba la consola. Ahora 4xx devuelve 200 con `{ok: false, reason: 'not_found'}` (soft fail — el ícono simplemente no se setea, el resto del autofill sigue); 5xx y errores de red siguen siendo 502/504.
